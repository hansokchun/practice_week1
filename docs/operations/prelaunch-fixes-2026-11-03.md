## 후속: 사용자 요청에 따른 Free 전환 · 2026-11-03

- 사용자가 무료 전환을 명시적으로 요청하여 조직의 Pro → Free 변경을 적용했다. Billing 화면에 `Free Plan`이 표시되는 것을 확인했다. 아래의 Pro 유지 문구는 전환 전 검수 시점의 기록이다.
- 전환 직전 청구기간(10월 7일~11월 7일) 일반 전송량 2.818GB, 캐시 전송량 0.071GB, 평균 Storage 0.341GB, MAU 3명, Micro 사용 642시간이었다. 일반 전송량은 무료 5GB의 약 56%다.
- 전환 과정에서 프로젝트 재시작 및 compute 하향 경고를 확인했다. 현재 데이터 삭제나 프로젝트 삭제는 실행하지 않았다.
- 전환 전 11월 2일 14:25 UTC 자동 물리 DB 백업을 확인했으나, 별도 DB 내보내기·사진 파일 백업은 생성하지 못했다. 기존 백업 스크립트는 Docker/DB 연결정보/암호가 준비되지 않았다. 자동 DB 백업은 Storage 실제 파일을 포함하지 않는다. 이 항목을 백업 완료로 취급하면 안 된다.
- 무료 전환 뒤 유예기간 종료 안내가 표시된다. 한도 초과 시 402 또는 서비스 제한이 가능하므로 전송량 경보 기준을 정하고 DB·사진 수동 백업을 준비해야 한다. 별도 모니터링 자동화는 생성하지 않았다.
- 요금제 변경은 공유 Supabase에 적용된다. 웹 코드·Cloudflare 운영 배포·Google Maps·AI 요금제는 변경하지 않았다.
- 재시작 과정에서 `RESIZING`을 관찰한 뒤 `ACTIVE_HEALTHY` 복귀를 확인했다. DB 조회 정상, 사진 175개·앨범 1개·사진 Storage 객체 391개 유지, DB 트랜잭션 읽기 전용 설정 `off`를 확인했다. 실제 업로드 시험을 한 것은 아니다.
- 운영 사이트 HTTP 200, 새 브라우저 탭에서 기존 로그인 세션 복원·사진 추가/프로필/알림 표시·공개 사진 목록과 화면 내 사진 파일 로딩·콘솔 오류 없음을 확인했다. 전환 완료 증거는 로컬 검수 폴더의 `screenshots/supabase-free-confirmed.png`에 보관했다.

## 수정 완료

- [x] 앨범 사진 추가·교체를 한 번의 `mutate_album_photos` RPC로 처리한다. 소유자 권한(RLS)을 유지하며, 연결 삭제 뒤 마지막 사진 갱신이 실패해도 이전 구성으로 전부 되돌아간다. 빈 선택 저장·순서·중복 제거·타인의 공개 사진 거부를 검증했다.
- [x] AI의 UTC 기준 사용자별 일일 30회 제한을 사진 상태가 아닌 비공개 사용량 원장에 기록한다. 분석 선점과 사용량 증가가 같은 DB 트랜잭션에서 실행된다. 사진 상태/시각을 초기화해도 31번째 분석은 차단된다. 실패한 분석 시도도 소비량에 포함하며, 한도 오류는 API에서 HTTP 429로 반환한다. 별도 유료 AI 호출 없이 검증했다.
- [x] 예전 `visibility=link` 사진·앨범의 목록 노출을 소유자만 볼 수 있도록 제한했다. `shared=true`인 옛 링크도 예외가 아니다. SECURITY DEFINER 좋아요 함수에도 같은 경계를 적용했다. 일반 공개·비공개, 차단 정책, 최신 모바일 `private+token` 공유 구조는 유지한다. 변경 전 실제 legacy link 사진/앨범은 모두 0개였다.
- [x] Vite를 8.2.4로 갱신하여 확인된 높은 위험도 개발 도구 취약점을 제거했다. 강제 수정으로 Capacitor를 구버전으로 내리지 않았다.
- [x] 사진 카드의 보조기기용 이름에 섹션 내 순서를 붙여 같은 “여행 사진” 버튼을 구분한다. 화면에 캡션을 추가하지 않는다.
- [x] 전체 화면 사진 랜딩의 `장소 저장소`를 흰색·그림자로 조정했다. 다른 페이지의 기존 브랜드 색과 글씨체는 유지한다.
- [x] 운영 출시 리허설에 기존 성능 예산 검사를 연결했다. 예산을 올리거나 검사 실패를 무시하지 않는다.

## 검증과 한계

- 신규 회귀 테스트는 수정 전 실패를 확인한 뒤 수정했다. 전체 Node 테스트·웹 빌드의 최종 결과는 아래 배포 기록에 남긴다.
- DB 테스트 파일 두 개를 같은 `BEGIN … ROLLBACK`에서 실행했다. 임시 사용자·사진·앨범·강제 실패 트리거를 사용했고, 테스트 자료는 커밋하지 않았다. 실제 사용자 사진을 업로드·삭제하지 않았다.
- 앨범 중간 실패 원복, 외부 사용자 사진 거부, 빈 앨범, 추가 저장, 30회 이후 차단, 사용자 원장 수정 거부, 익명/다른 계정의 legacy 조회·좋아요 거부와 기존 공개 사진 읽기를 확인했다.
- 일일 한도 동시성은 DB UPSERT의 행 잠금으로 직렬화한다. 별도의 다중 세션 부하 시험을 수행한 것은 아니다.
- 보안 진단의 비공개 원장 “RLS 정책 없음”은 직접 접근 차단을 위한 의도된 상태다. 클라이언트용 정책을 추가해 경고를 없애면 안 된다. 기존 인증 사용자용 SECURITY DEFINER 알림·좋아요 함수 두 개는 권한 검사를 유지한다. [진단 설명](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)
- 사용되지 않은 인덱스 11개는 낮은 트래픽 때문에 사용 기록이 없는 것일 수 있어 삭제하지 않았다.

## 아직 남은 운영 관문

- [ ] 로그인한 실제 브라우저에서 업로드 → 앨범 저장/교체 → 공개/비공개 → 로그아웃 후 접근 → 삭제까지 전체 회귀 검수. DB 권한 테스트와 보조 함수 테스트만으로 이 항목을 완료 처리하지 않는다.
- [ ] 목록 조회를 화면/지도 범위별 서버 페이지네이션으로 전환. 현재는 200개씩 나눠 모든 보이는 사진 메타데이터를 모으므로 데이터가 많아지면 초기 대기·전송량이 증가한다. 단순히 첫 200장으로 잘라 사진을 누락시키는 변경은 하지 않았다.
- [ ] 번들/CSS/정적 이미지 최적화. 현재 전체 JS Brotli 306.43KiB / 예산 70.5, CSS 36.36 / 30, 이미지 합계 2,435.87 / 2,200. 최대 단일 이미지 348.74 / 450은 통과한다. 앨범 다운로드용 큰 JS는 지연 로딩되므로 전체 JS 합계를 첫 진입 전송량이라고 해석하면 안 된다.
- [ ] 개발 도구에 남은 moderate 4개(Capacitor CLI → rimraf → glob/minimatch)의 호환성 검증 후 갱신. 웹 런타임 의존성에는 audit 취약점이 없다.
- [ ] CSP의 inline/eval 허용을 외부 SDK별로 줄이고, 상세 지도 fallback의 구형 Marker를 교체한다. 현재 경고를 실제 공격/서비스 장애로 단정하지 않는다.
- [ ] 하단 고정 지도 버튼의 중간 섹션 가림은 디자인 개선 대상으로 남긴다. 사용자 지정의 고정 진입 방식을 임의로 없애지 않았다. 마지막 푸터의 하단 여백은 이미 존재한다.

자산 캐시 정책은 과거 HTML이 CSS 경로에 캐시된 장애 기록이 있어 무조건 `immutable`로 바꾸지 않았다. 프런트엔드 운영 승격은 위 관문과 재검증 뒤 별도로 진행한다.

## Supabase 무료 전환 판단

현재 요금제는 Pro다. 이번 작업에서는 구독을 변경하지 않았다.

| 항목 | 확인한 현재 값 | Free 한도 |
| --- | ---: | ---: |
| DB 크기 | 수정 전 약 15.5MB | 500MB |
| 사진 Storage | 약 347MB, 객체 391개 | 1GB |
| 월 일반 전송량 | 미확인 | 5GB |
| 월 캐시 전송량 | 미확인 | 5GB, 일반 전송량과 별도 |
| 월 활성 사용자 | 미확인 | 50,000명 |

객체 수는 원본·썸네일·미리보기 파일을 포함하므로 사진 수와 다르다. 월 전송량·사용자 수는 관리 콘솔 로그인이 필요해 확인하지 못했다. 사진 변환은 현재 앱의 자체 썸네일/미리보기 파일 방식이라 Supabase의 유료 이미지 변환 기능을 호출하는 코드는 확인되지 않았다. [공식 요금표](https://supabase.com/pricing)

### 속도와 운영상 변화

- 사이트 HTML/JS/CSS는 Cloudflare에서 제공하므로 Supabase를 Free로 바꾼다는 이유만으로 이 파일들의 제공 서버가 느려지지는 않는다.
- 로그인·사진 목록·앨범 등 DB 작업은 무료 공유 자원에서 동시 요청이 늘면 느려질 수 있다. 현재 실제 compute 등급은 별도 확인이 필요하다. Pro라는 이유만으로 반드시 Micro라고 단정하지 않는다. [Compute 설명](https://supabase.com/docs/guides/platform/compute-and-disk)
- 사진 전달은 Storage·캐시 영향을 받는다. 유료 Smart CDN 기능 차이가 있어 같은 속도를 보장할 수 없다. [Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn)
- 활동이 적은 무료 프로젝트는 약 7일 뒤 일시 중지될 수 있다. 이때 사이트 틀은 떠도 로그인/사진 데이터는 복구 전까지 정상 동작하지 않을 수 있다. [일시 중지 정책](https://supabase.com/docs/guides/platform/free-project-pausing)
- Pro의 자동 일일 백업 보관 혜택이 사라진다. 무료 전환 전 DB와 Storage 파일을 각각 백업해야 한다. DB 백업만으로 실제 사진 파일이 보관되지는 않는다.
- 구독은 조직 단위이고 다운그레이드는 즉시 적용된다. 다른 프로젝트·유료 추가 기능·기존 초과 사용료도 확인해야 한다. [구독 변경](https://supabase.com/docs/guides/platform/manage-your-subscription)
- Supabase를 무료로 바꿔도 Google Maps/Street View, Cloudflare AI의 별도 비용은 없어지지 않는다.

### 권장 순서

1. 최근 30일 일반/캐시 전송량과 같은 조직의 다른 프로젝트·유료 추가 기능을 확인한다.
2. DB와 사진 파일 백업을 만들고 복원 방법을 확인한다.
3. 운영 전 소규모 테스트라면 Free 전환을 검토할 수 있다. 현재 저장 용량만 보면 가능하다. 실제 사용자 사진을 안정적으로 보관하는 공개 운영이라면 자동 백업·중단 방지를 위해 Pro 유지가 더 안전하다.
4. 전환 후 로그인·사진 조회·업로드 속도를 같은 조건에서 비교한다. 사용자 수보다 Storage/전송량/응답 지연으로 재업그레이드를 판단한다.
5. 운영 경보 기준의 제안값은 Storage 800MB, 각 전송량 한도의 70~80%다. 공식 제한이 아니라 한도 도달 전에 대응하기 위한 내부 기준이다.

## 배포 기록

- 전체 자동 테스트 1,396개와 웹 빌드 통과. `npm audit --omit=dev`는 0건이다.

- 코드 커밋 `6437393`을 `origin/dev`에 푸시했다. Cloudflare 개발 배포 `8678d6bf`가 Active임을 확인했다. 개발 별칭에서 새 사진별 이름·공개 목록·지도 경로 진입과 콘솔 오류 없음, 비인증 AI 요청의 401 차단을 확인했다.
- 개발 미리보기: <https://dev.practice-week1-cws.pages.dev/?ui=6437393#/home>. 운영 main 프런트엔드는 올리지 않았다. 공유 DB 보호는 운영에도 이미 적용되며 기존 운영 AI API는 한도 차단을 일반 오류로 안내할 수 있어 최종 운영 승격 시 새 API를 함께 반영해야 한다.
