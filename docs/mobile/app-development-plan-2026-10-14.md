## 1. 이번에 확정한 목표

앱은 현재 웹의 페이지, 기능, 서버 사진을 같은 서비스로 제공한다. 앱의 `내 사진`은 로그인한 사용자가 서버에 저장한 사진이다. 다른 기기나 웹에서 올린 사진도 같은 계정으로 로그인하면 보인다. 휴대전화 사진은 `사진 추가`에서 사용자가 선택할 때만 읽는다.

전체 기기 보관함 인덱싱, 로컬 사진 지도, SQLite 사진 목록을 앱의 기본 제품 흐름에서 제외한다. 기존 소스와 미완료 업로드 작업은 전환 검증 전까지 보존한다. 보관함 접근 권한을 거부해도 서버 사진과 앨범을 이용할 수 있어야 한다.

동일한 계정이란 같은 Supabase 사용자 ID와 서버 데이터를 사용하는 것이다. 웹 브라우저와 앱의 로그인 세션이 자동으로 공유된다는 의미는 아니다. 각 환경에서 로그인하되 게시·수정·삭제 결과는 다시 조회하면 같아야 한다.

## 3. 웹 코드를 앱에서 사용하는 방식

**개발 방향은 현재 Vite 웹 코드를 재사용하는 Capacitor 앱이다.** 웹 화면과 기능을 한 원본에서 관리하고, 사진 선택·파일 저장·공유·외부 인증 복귀만 앱 기능으로 연결한다. 계획 작성 이후 시험 컨테이너를 추가했으며, 운영 런타임 확정은 실제 설치·인증·지도 검증을 통과한 뒤로 유지한다.

| 방식 | 웹 변경 반영 | 기존 코드 재사용 | 이번 목표와의 관계 |
| --- | --- | --- | --- |
| 기존 Expo 화면 계속 개발 | 웹 변경마다 별도 화면 수정 | 기존 네이티브 화면·모듈 재사용 높음 | 기능 차이를 계속 대조해야 함 |
| Expo 안에 WebView 추가 | 웹 원본 재사용 가능 | 기존 앱 껍데기 재사용 가능 | 인증·파일·공유 연결을 별도로 설계해야 함 |
| Capacitor에 웹 빌드 포함 | 같은 웹 원본으로 웹·앱 빌드 | 현재 웹 페이지·앨범·관리 기능 재사용 높음 | 기본 권장안; 1단계에서 호환성 검증 |

Capacitor는 기존 JavaScript 프로젝트에 앱 컨테이너를 추가하고 웹 빌드를 네이티브 프로젝트에 복사하는 방식을 제공한다. 배포 앱에는 검증한 웹 번들을 포함하는 구성을 기본으로 한다. [Capacitor 소개](https://capacitorjs.com/docs), [빌드·동기화 과정](https://capacitorjs.com/docs/basics/workflow)

서버 사진·큐레이션·좋아요·댓글 변경은 같은 백엔드 재조회로 반영된다. **웹 화면을 배포했다고 설치된 앱 번들이 즉시 바뀌는 것은 아니다.** 화면 코드 변경은 동일 소스의 앱 빌드·배포 과정으로 반영한다. 원격 웹 URL 상시 로딩이나 별도 실시간 코드 업데이트는 기본 계획에 넣지 않는다. Capacitor의 `server.url`은 공식 문서에서도 개발용으로 설명한다. [Capacitor 설정](https://capacitorjs.com/docs/config)

### 첫 기술 검증에서 반드시 확인할 것

- 현재 `/api/config`·사진 AI·관리자·공유 API의 상대 주소를 앱에서도 올바른 HTTPS 서버로 연결한다. CORS, CSP, 세션 전달, 지도 키 제한과 외부 SDK를 함께 검사한다.
- OAuth는 지원되는 외부 인증 화면에서 열고 앱으로 돌아온 뒤 PKCE·세션을 이어 간다. 현재 웹 redirect helper가 로컬 주소를 웹 미리보기로 보내는 동작도 앱 전용 분기로 조정해야 한다. Google 인증은 임베디드 WebView에서 막힐 수 있다. [Google 네이티브 OAuth 안내](https://developers.google.com/identity/protocols/oauth2/native-app)
- 휴대전화 선택 파일을 웹 업로드가 소비할 수 있는 형식으로 전달하고, HEIC·방향·촬영일·위치를 보존하는 처리 경계를 검증한다.
- 웹 Google Maps·Places·정적/동적 거리뷰와 Turnstile·카카오 SDK의 앱 origin 호환성을 확인한다. 실패하면 해당 연결부에 필요한 네이티브 adapter만 둔다.
- 앱 안전 영역·키보드·뒤로가기·다운로드·공유를 실제 컨테이너에서 검사한다. Expo Web 내보내기를 기기 기능 검증으로 사용하지 않는다.

이 검증을 통과한 뒤 앱 컨테이너를 확정한다. 기존 Expo 소스는 비교·복구 기준으로 보존하며, 두 개의 제품 화면을 계속 병행 개발하지 않는다.

## 4. 새 앱 범위와 데이터 계약

### 서버 사진과 독립 업로드

- `내 사진`: 현재 Auth 사용자 소유의 `photos`를 조회한다. 웹에서 올린 사진, 앱에서 올린 사진이 함께 보인다.
- 정렬: 등록 순, 촬영 최신순, 촬영 오래된 순. 웹과 같은 16장 페이지와 선택 유지 규칙을 따른다.
- 일괄 공개·비공개·삭제는 같은 서버 제한과 권한을 적용한다. 공개 범위 변경으로 저장 위치나 정확도를 바꾸지 않는다.
- `사진 추가`: OS 선택창 → 파일 검증·최적화 → 업로드 → 완료 화면 → 위치 누락 처리 순서다. 전체 보관함 스캔은 하지 않는다.
- 원본·목록 썸네일·preview 경로와 촬영일, 위치, `shared`·`visibility`, AI 분석 상태를 웹과 같은 계약으로 저장한다.
- 사진 선택 취소·부분 실패·중단 재개에서 원본을 보존하며, 기존 미완료 로컬 작업은 전환 전에 확인해 재시도 또는 사용자 취소 경로를 제공한다.

### 웹 전체 사용자 기능

- 전체 화면 랜딩, 공개 메인, 검색, 태그 전체보기, 지도, 사진 상세, 업로드 완료·위치 지정 페이지를 포함한다.
- 앨범 생성·사진 선택/정렬·편집·삭제·표지·공개 범위·공유를 포함한다. 제목 없는 앨범도 같은 방식으로 저장·표시한다.
- 공개 앨범과 멤버 사진의 공개 범위는 독립적으로 유지한다. 앨범 공개가 멤버 사진을 임의로 공개하지 않는다.
- 프로필 커버·아바타·소개, 공개 사진·앨범·지도, 받은 좋아요·읽음, 가입 안내·계정 경고를 포함한다.
- 사진 AI는 현재 웹의 서버 분석·검색 계약을 재사용한다. 미래 AI 자동 앨범은 웹에서도 미출시이므로 이번 범위에 추가하지 않는다.
- 사진/앨범 링크 복사·카카오 공유·시스템 공유와 GPS가 포함된 다운로드 복사본을 제공한다. 서버 원본 파일은 수정하지 않는다.
- 웹 관리자 페이지는 같은 권한을 가진 운영자가 사용하는 기존 페이지를 재사용한다. 일반 사용자에게 운영 메뉴를 노출하거나 앱에서 권한을 우회하지 않는다.

### 위치·설정·공유에서 정리할 정책

- 정확/대략 위치는 지점에 대한 확신 정도이며 현재 웹처럼 선택 좌표를 이동시키지 않는다. 공개 여부는 별도다. 대략 위치의 좌표 표시와 거리뷰 노출은 최신 웹과 일치시킨다.
- 현재 앱은 대략 위치에서도 외부 거리뷰를 열지만 현재 웹 상세는 정확 위치에서 미리보기·동적 거리뷰를 제공한다. 새 앱은 웹 상세 기준으로 맞춘다.
- 웹 계정 설정은 localStorage, 앱 설정은 AsyncStorage에 있어 기본값·알림 설정이 자동으로 공유되지 않는다. 우선 동일 동작과 키 의미를 맞춘다. 기기 간 설정 동기화가 필요한 항목은 서버 저장 여부를 별도로 정한다.
- 모바일 비밀 토큰 링크와 웹 공개 사진·앨범 링크는 접근 계약이 다르다. URL·공개 범위·수신 화면을 함께 검증하고 기존 링크를 유지하는 호환 경로를 만든다.
- 최신 RLS·계정 차단·신규 계정 제한·좋아요 RPC를 기준으로 갱신한다. 앱 조회 실패를 전부 네트워크 오류로 처리하지 않는다.

## 10. 승인 후 시험본 구현 진행 — 2026-10-14

현재 단계는 **웹 재사용 앱의 소스·연결 계층 구현 완료, 실제 설치 검증 대기**다. 앱 전체 출시 완료나 단계 1 실기기 통과를 의미하지 않는다. 기존 `mobile/` Expo 소스와 기기 보관함 데이터는 삭제하지 않았다.

### 이번에 반영한 범위

- 같은 `index.html`, `js/app.js`, `auth.js`를 웹과 앱의 공통 원본으로 사용한다. 앱용 번들은 `app-shell/www`, 웹용 번들은 `dist`로 분리한다. 따라서 앱의 내 사진·사진 추가·앨범 편집은 웹의 서버 기반 구현이며 기존 Expo 기기 보관함 화면을 실행하지 않는다.
- `app-shell/android`, `app-shell/ios`에 Capacitor 8 프로젝트를 생성했다. 앱 식별자는 기존과 같은 `com.ikkyee.mobile`이며, 원격 웹 상시 로딩·혼합 HTTP·자동 fetch 전역 패치는 사용하지 않는다.
- 앱의 `/api/config`, `/api/analyze-photo`를 운영 HTTPS 서버로 연결한다. 인증 헤더는 유지하고 상대 API 이외 주소, 경로 우회, 자동 HTTP redirect는 거절한다.
- Google·Kakao는 외부 인증 브라우저와 `ikkyee://auth/callback` PKCE 복귀를 사용한다. 세션·verifier는 Android Keystore 기반 암호 저장소/iOS 기기 전용 Keychain에 보관하며 평문 웹 저장소로 폴백하지 않는다.
- 이메일 가입·비밀번호 복구도 같은 앱 콜백으로 돌아오도록 분기했다. SDK의 복구 식별을 사용하며 중단된 로그인은 사용자가 명시적으로 취소하고 다시 시도할 수 있다.
- 공개 사진·앨범 공유는 앱에서 OS 공유창을 사용한다. 웹의 카카오 공유와 링크 복사는 유지한다. 앱에서 만든 링크의 origin은 localhost가 아니라 `https://ikkyee.com`이다.
- 다운로드는 웹의 JPEG 변환/GPS EXIF 파이프라인을 유지한 뒤 앱 캐시에 복사하고 OS 저장·공유 선택창으로 전달한다. JPEG·PNG·WebP를 지원하고 50MiB를 초과하면 준비 전에 거절한다. OS 창 종료를 갤러리 저장 성공으로 표현하지 않는다.
- Android 뒤로가기는 열린 창 → 앱 내부 이전 화면 → 시작 화면 → 사용자 확인 후 종료 순서다. 안전 영역 스타일을 추가하고 정책·지원 문서와 사진 위치 링크는 허용한 외부 HTTPS 주소로 연다.
- 앱 HTML에는 기존 웹 CSP에서 meta로 지원되는 항목을 반영했다. 인코딩 선언을 먼저 두며 Android 백업·기기 이전에서 앱 데이터가 제외되도록 설정했다. iOS Filesystem FileTimestamp 사용 사유를 리소스로 등록했다.
- 고정 브랜드 마스터를 변경하지 않고 앱 아이콘·스플래시 PNG 30종과 지문 원장을 생성했다. 네이티브 SDK는 웹 빌드에서 제외해 웹에 앱 패키지를 추가로 배포하지 않는다.

### 다음 작업과 사용자 참여 지점

1. 시험 휴대전화는 이후 사용자 응답으로 Android로 확정됐다. Android APK를 먼저 준비하며 iOS 실제 설치는 이번 시험 경로에 포함하지 않는다.
2. 해당 플랫폼의 무료 로컬 빌드 도구를 준비한다. Android는 Android Studio/SDK/JDK 및 SDK 약관 확인, iOS는 지원 Xcode와 실제 설치용 서명 준비가 필요하다. 시스템 설치·약관 동의나 계정 자격 증명이 필요하면 사용자에게 요청한다.
3. Supabase 허용 redirect에 앱 콜백이 실제 등록됐는지 확인한다. Google Maps/Places/거리뷰 키 제한과 Turnstile이 Android `https://localhost`, iOS `capacitor://localhost` 환경에서 동작하는지 검사한다. 허용 설정을 넓히거나 보안 확인을 끄지 않는다.
4. 새 앱을 실제 설치하고 같은 테스트 계정으로 웹↔앱 서버 사진·앨범 왕복, 선택한 사진만 업로드, 권한 거부, 프로세스 종료/복귀, OS 공유 취소·저장을 확인한다. 현재 Supabase UMD·폰트·지도 SDK는 CDN 의존성이 남아 있어 최초 오프라인 실행도 별도 검증한다.
5. 공개 웹 공유 링크의 앱 수신(Universal/App Links)은 앱 콜백 등록과 별개다. 도메인 연결 파일·서명/팀 정보·수신 라우트가 준비되기 전에는 설치 앱으로 링크가 자동 열린다고 안내하지 않는다. 기존 모바일 비밀 토큰 링크도 유지 검증 대상이다.
6. 기존 APK와 같은 식별자이므로 서명·versionCode·미완료 업로드 유지 조건을 대조하기 전에는 업데이트 설치 완료로 표시하지 않는다. 기존 앱 제거·데이터 초기화는 진행하지 않는다.

이 절은 SDK 설치 승인 전의 준비 이력이다. 이후 승인과 실제 APK 결과는 12절을 우선한다. 사용자가 시험 기기를 **Android**로 답했다. 당시 SDK 약관 동의 응답은 아직 확인되지 않아 SDK 다운로드·설치·실행과 약관 수락을 보류했다.

### 완료한 준비

- Eclipse Adoptium 공식 배포 정보를 확인하고 Temurin Java 21.0.12.1+1 macOS ARM 배포본을 SHA-256 검증 후 `app-shell/.toolchain/java/`에 압축 해제했다. 실제 `java`·`javac` 버전 실행을 확인했다. 시스템 Java/PATH나 다른 프로젝트 설정을 바꾸지 않았다.
- Gradle 8.14.3의 공식 binary 배포 SHA-256을 wrapper에 고정했다. 프로젝트 전용 Gradle 캐시에서 실제 Gradle 버전 실행까지 통과했다. 크기가 더 큰 `all` 배포 대신 동일 버전의 `bin` 배포를 사용한다.
- 앱 Build Tools를 36.0.0으로 고정했다. Capacitor 라이브러리의 AGP 기본값에 따라 첫 빌드에서 35.0.0이 추가로 필요할 수 있으며 실제 Gradle 결과로 확인한다.
- 시험용 debug 서명 키의 위치를 ignored 프로젝트 도구 폴더로 분리했다. 출시 서명 키가 아니며 이번 준비 점검에서는 키 생성·휴대전화 설치를 실행하지 않았다.
- 읽기 전용 준비 검사와 Android 시험 APK 빌드 명령을 추가했다. 설치된 SDK 패키지의 약관 본문과 기존 동의 기록을 비교할 뿐, 약관 기록을 만들어 검사에 통과시키지 않는다.

```bash
npm run app:doctor:android
npm run app:apk:android
```

첫 명령은 Node/Java/SDK/API 36/Build Tools/adb/SDK 약관/프로젝트 동기화와 앱 식별자 일치를 읽기 전용으로 점검한다. 두 번째는 웹 원본의 앱 번들·동기화 후 준비 검사 → debug 단위 테스트 → lint → APK 빌드를 실행한다. **준비 검사 실패 시 컴파일·서명 파일 생성으로 넘어가지 않는다.** 준비·키 생성·Gradle 실패 시 이전 APK를 새 산출물로 복사하지 않는 제어 흐름을 주입 테스트로 검증했다. 성공한 뒤에만 `app-shell/artifacts/android/ikkyee-android-debug.apk`와 파일 지문·생성 시각·입력 시작 문서 지문 원장을 생성한다. 기기 설치, 업데이트, 외부 배포, SDK 자동 동의는 명령에 없다.

## 12. Android 시험 APK 생성·검증 완료 — 2026-10-14

SDK 설치·약관 확인 요청에 사용자가 “진행해줘. 계속 너가 판단대로 진행해”라고 답했다. 해당 요청 범위의 승인으로 진행했으며 별도의 유료 서비스나 운영 배포 승인을 뜻하지 않는다.

### 사용자 흐름별 확인 및 수정

1. **랜딩 → 사진 탐색 → 상세:** 390×844에서 기존 웹 구성 유지. 상세 좋아요의 실제 터치 영역이 22×22px인 것을 측정하고 44×44px로 확대했다. 아이콘 크기는 22px 유지. 공유창 닫기·복사, 앨범 다운로드 닫기도 44px 기준으로 개선했다.

3. **사진 작성자 → 공개 프로필:** 실제 공개 웹에서 작성자와 다른 소유자 프로필로 이동함을 재현했다. 모든 `data-public-album-id` 요소에 바인딩되던 앨범 클릭 처리가 작성자 버튼을 덮어썼다. 중복 바인딩을 제거하고 기존 `data-go-trip` 위임 흐름을 유지했다. 개발 배포에서 작성자 버튼 ID와 이동 URL 소유자 ID·표시 이름이 일치함을 확인했다.

## 15. 앱 메인 직행·시작 애니메이션·로그인 무반응 대응 — 2026-10-18

사용자의 최신 요구에 따라 **앱에서는 랜딩 화면을 제거하고 메인으로 바로 진입**한다. 웹의 랜딩은 유지한다. 이전 절의 랜딩 재사용 계획보다 이 결정이 우선한다.

- Native 빌드에서만 랜딩 마크업을 제거하고 메인/헤더 로고의 목적지를 `#/`로 바꿨다. 기존 랜딩 경로와 Android 뒤로가기의 기본 목적지도 메인으로 정규화한다. 사진·앨범·프로필 공유 경로는 유지한다.
- 고정 로고 `images/logo.png`를 그대로 사용한 휴대전화용 CSS 시작 애니메이션을 추가했다. 세로 이동·페이드인과 로딩 점을 사용하며 로고 원본, 비율, 색은 변경하지 않았다. 안전 영역, 작은 화면, 동작 줄이기 설정을 반영하고 인위적인 최소 대기시간은 두지 않았다. 12초 지연 시 안내와 재연결 버튼을 제공한다.
- 로그인 모달에 `로그인 없이 둘러보기`를 넣었다. 공개 사진·지도·공개 앨범/프로필은 비로그인 접근을 유지하고 업로드·설정 등 계정 기능의 로그인 요구는 보존한다. RLS, 공개 범위, 서버 데이터는 변경하지 않았다.
- 사용자가 로그인 실패를 **상단 로그인 버튼을 눌러도 반응 없음**으로 구체화했다. UI 이벤트를 플러그인/세션 복원보다 먼저 연결하고, 동적 프로필 컨트롤 생성 순서는 보존했다. 이미 DOM 준비 이벤트가 끝난 뒤 모듈이 실행돼도 초기화가 실행되도록 보강했다. 이것이 해당 기기의 확정 원인이라는 실기기 재현 증거는 아직 없다.
