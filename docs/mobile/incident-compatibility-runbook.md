# 모바일 장애·호환성 운영 지침

**작성일:** 2026-08-25  
**적용 범위:** Ikkyee iOS·Android 앱, 기기 로컬 데이터, 웹과 공유하는 Supabase, 모바일 Edge Function·Storage

## 현재 복구 능력

현재 앱은 `expo-updates`를 설치하거나 구성하지 않았다. `eas.json`의 EAS build `channel`은 빌드가 속할 배포 채널 이름일 뿐, 현재 상태에서는 OTA 업데이트나 OTA 롤백이 아니다. 앱 코드 회귀는 스토어 배포 중단, 마지막 정상 소스의 정상적인 `git revert`, 빌드 번호 증가, TestFlight·Play 내부 테스트 검증, 스토어의 새 바이너리 배포 순서로 복구한다.

EAS Update는 별도 제품·보안 승인, Expo 프로젝트 연결, `expo-updates`, `updates.url`, `runtimeVersion`, 미리보기·운영 채널 검증을 마친 뒤에만 도입한다. 도입 승인 전에는 `eas update`, republish, rollback 명령을 운영 복구 수단으로 기록하거나 실행하지 않는다.

## 심각도와 최초 대응

| 등급 | 예시 | 최초 대응 목표 | 즉시 조치 |
| --- | --- | --- | --- |
| P0 | 비공개 사진·정확 위치 노출, 계정 탈취, 데이터 파괴 | 즉시 확인, 15분 안에 확산 차단 시작 | 배포·게시 쓰기 중지, 안전한 기능만 유지, 개인정보 담당 호출 |
| P1 | 로그인·Explore·게시·계정 삭제 등 핵심 기능 다수 실패 | 30분 안에 담당·완화책 결정 | 최근 앱·백엔드 변경 분리, 정상 읽기 경로 우선 복구 |
| P2 | 일부 기기·공급자·사진 형식 실패, 성능 급락 | 4시간 안에 우회책·수정 계획 | 영향 범위 제한, 재시도·기능 축소, 다음 후보에서 수정 |
| P3 | 문구·레이아웃·낮은 영향의 비핵심 결함 | 다음 업무일 분류 | 기록 후 정상 출시 절차로 수정 |

모든 등급에서 시각, 앱 버전·빌드 번호, 플랫폼, 환경, 최초 증상, 영향 기능, 마지막 정상 버전, 최근 앱·DB·Edge Function 변경을 기록한다. 이메일, access token, 사용자 ID, 사진 ID·URL, Storage 경로, 설명, 정밀 좌표, 원본 사진이나 개인정보를 로그에 남기지 않는다.

## 차단과 진단 순서

1. 새 production 빌드·백엔드 배포·데이터 정리를 중지한다.
2. 문제가 앱 바이너리, 공유 백엔드, Edge Function, 네트워크, 로컬 SQLite·캐시 중 어디에서 시작했는지 분리한다.
3. 익명·소유자·비소유자 역할, iOS·Android, 현재 버전과 N-1 버전으로 최소 재현한다.
4. 개인정보 노출이면 사용 편의보다 노출 차단을 우선하되 RLS를 끄거나 private bucket을 public으로 바꾸지 않는다.
5. 변경 전후의 집계 상태와 migration history만 보존하고 사용자 행·원본 객체를 증빙으로 복사하지 않는다.

## 표면별 되돌리기

| 표면 | 기본 복구 | 금지 사항 | 확인 |
| --- | --- | --- | --- |
| 앱 바이너리 | 스토어 출시·단계 배포 중지 → 정상 소스 revert → 새 빌드 번호로 내부 테스트 → 새 바이너리 | 이미 배포된 바이너리를 원격으로 사라지게 할 수 있다고 가정하지 않기 | 설치·업그레이드, 로그인, 로컬 사진, Explore, 게시, 삭제 |
| RLS·Storage | 마지막 정상 정책을 새 순방향 migration으로 복원하고 역할 검증 | RLS를 끄지 않는다. private bucket을 public으로 바꾸지 않는다 | 익명·소유자·비소유자 및 서명 URL 만료 |
| Edge Function | 현재 DB 계약과 호환되는 마지막 정상 소스를 새 버전으로 배포 | 인증 검증 제거, secret을 앱에 이동, 오래된 함수가 새 스키마를 지원한다고 가정 | 401·4xx·정상 요청, 최소 응답 필드, 멱등성 |
| 로컬 SQLite | 스키마 버전을 올리는 순방향 수정 또는 파생 데이터 재인덱싱 | `user_version` 하향, 원본 기기 사진 삭제, 손상 DB로 원본 자산 수정 | fresh·upgrade·corruption·invalid 시나리오 |

DB 하향 마이그레이션은 기본적으로 금지한다. 이미 실행 중인 웹과 구버전 앱이 새 스키마로 쓰기 시작했을 수 있으므로, DROP·RENAME·타입 축소나 데이터 역변환은 복구보다 추가 손상을 만들 수 있다. 데이터 독립적이고 N/N-1 클라이언트·백업 복원 검증까지 끝난 예외만 별도 승인한다.

어떤 복구에서도 원본 기기 사진은 삭제하지 않는다. 앱이 다시 만들 수 있는 SQLite 색인, 썸네일, 게시 파생본만 정해진 정리 절차의 대상이다.

## 공유 백엔드 호환 절차

웹과 모바일은 같은 운영 Supabase를 사용하므로 최소 N과 N-1 앱, 현재 웹을 동시에 지원한다. 변경은 다음 확장 → 이행 → 축소 순서만 허용한다.

1. **확장:** nullable 열·새 테이블·새 함수·새 정책처럼 기존 읽기·쓰기를 보존하는 migration을 먼저 추가한다. exposed schema의 테이블은 RLS와 Data API grant를 각각 검토한다.
2. **이행:** Preview 프로젝트에서 전체 migration 재생, 역할·Storage·Edge Function 검증 후 운영에 순서대로 적용한다. 새 앱은 구·신 계약을 안전하게 읽고 필요한 기간 dual-read 또는 서버 기본값을 사용한다.
3. **관찰:** 웹, N, N-1의 오류율·핵심 왕복·버전 채택을 확인한다. 구버전이 남아 있는 동안 열·함수·정책을 제거하지 않는다.
4. **축소:** 지원 종료가 승인되고 N-1 트래픽이 허용 기준 아래임을 확인한 다음 별도 migration으로 레거시 계약을 제거한다.

DB migration은 앱보다 먼저 배포하고, migration history와 저장소 파일이 일치하는지 확인한다. 운영 Dashboard에서 직접 스키마를 고치지 않는다. 실패 시 migration history만 억지로 수정하지 말고 실제 스키마 상태를 먼저 비교한다. Edge Function 응답은 구버전이 모르는 필드를 무시할 수 있게 추가형으로 변경하고, 기존 필드 삭제·의미 변경은 새 endpoint나 버전 계약으로 분리한다.

## 강제 업그레이드

강제 업그레이드는 현재 구현하지 않았다. 다음 중 하나가 확인되고 서버 호환 유지나 기능별 차단으로 해결할 수 없을 때만 사용한다.

- 악용 중인 보안·개인정보 취약점
- 구버전 쓰기가 데이터 손상이나 권한 우회를 일으키는 경우
- 공급자·플랫폼의 필수 변경으로 인증 등 핵심 기능이 영구적으로 불가능한 경우

먼저 새 스토어 빌드를 내부 테스트하고 배포한 뒤 채택률과 복구 경로를 확인한다. 최소 지원 버전과 스토어 URL은 저장소 상수가 아니라 승인된 외부 설정으로 운영하며, 값의 변경 기록·담당자·만료 시각을 남긴다. 버전 확인 실패만으로 앱 전체를 닫지 않는다. 구버전의 위험한 서버 쓰기만 안전하게 거부하고, 로컬 사진 탐색과 오프라인 로컬 접근은 유지한다. 차단 화면은 이유, 현재 버전, 필요한 버전, 스토어 이동, 재시도를 제공하며 로그에 계정·사진 정보를 넣지 않는다.

## 향후 EAS Update를 도입할 경우

도입 승인 뒤에는 `runtimeVersion`을 `appVersion` 정책으로 명시하고 네이티브 의존성·Expo SDK·로컬 모듈이 바뀔 때 앱 버전과 새 바이너리를 함께 올린다. Preview에서 같은 runtime과 번들을 검증한 뒤 production에 단계 배포한다. 롤백 전에는 깨진 업데이트가 SQLite·AsyncStorage·파일을 비호환 방식으로 변경했는지 확인한다. 그렇다면 이전 업데이트 재게시 대신 순방향 수정이 기본이다.

## 종료 근거

장애는 다음이 모두 충족될 때만 종료한다.

- 원인, 영향 버전·환경·기간과 사용자 영향이 기록됨
- 완화 또는 수정 버전에서 핵심 왕복과 역할 검증이 통과함
- N/N-1 웹·모바일 호환과 로컬 원본 보존이 확인됨
- 비밀값·개인정보 없는 로그와 변경 ID·빌드 번호·migration 목록이 남음
- 후속 테스트, 재발 방지, 문서·체크리스트 갱신 담당이 지정됨
